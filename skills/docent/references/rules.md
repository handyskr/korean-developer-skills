# 읽는 사람이 한 번에 이해하는 글의 규칙

## 목차

- 범위
- 1. 쓰기 전에: 1-1 질문 한 문장, 1-2 읽는 사람, 1-3 글 종류, 1-4 원본이 아니라 주제를 쓴다, 1-5 보태는 지식
- 2. 낱말과 가리키기: 2-1 처음 나오는 용어, 2-2 지어낸 이름, 2-3 찾아갈 수 있는 이름, 2-4 번호와 지시어, 2-5 비유, 2-6 화면과 같은 이름
- 3. 내용: 3-1 지금 상태 먼저, 3-2 왜 묻는지, 3-3 설명마다 실제 모습, 3-4 옮겨 적지 않기, 3-5 확인과 추측, 3-6 묻지 않은 것
- 4. 그림: 4-1 그림 종류, 4-2 큰 그림 먼저, 4-3 참여자, 4-4 화살표 글씨, 4-5 빠진 것, 4-6 범례, 4-7 나누기, 4-8 움직이는 그림, 4-9 렌더 확인
- 내보내기 전 점검

## 범위

이 파일은 읽기 어려운 문서·대화 내용·작업 결과물을 **이해할 수 있게 풀어 쓸 때** 무엇을 담고 어떤 순서로 둘지, 그림을 어떻게 그릴지를 다룬다.

| 이 파일 | korean-sentences의 `rules.md` |
|---|---|
| 무엇을 쓸지: 용어 설명, 실제 이름, 예시, 지금 상태, 그림 | 어떻게 말할지: 낱말, 수 세기, 문장 순서, 말투, 띄어쓰기 |
| 원본의 내용은 지키고 구성은 다시 짠다. 읽는 데 필요한 지식만 조사해서 짧게 보탠다 | 이미 있는 글을 다듬고 사실은 더하지 않는다 |

두 파일을 함께 따른다. 규칙마다 ✗ 나쁜 예와 ○ 좋은 예를 둔다. 규칙을 고치면 그 계기를 `cases.md`에 사례로 남긴다.

## 1. 쓰기 전에

**1-1. 이 글이 답할 질문을 한 문장으로 정한다**
- 질문은 원본이 이야기하려는 것에서 잡는다.
- 질문이 둘이면 글이나 절을 나눈다. 그림마다 위에도 그 그림이 답하는 질문을 한 줄 둔다.
- ○ 이 글이 답할 질문: 로그인 요청이 어떤 서버를 거쳐 어떤 토큰으로 돌아오는가

**1-2. 읽는 사람이 아는 것과 모르는 것을 나눈다**
- 글쓴이가 작업 중에 본 것은 모두 모르는 것으로 둔다. 대화 앞부분, 작업 문서, 서브에이전트 보고, 내가 붙인 이름이 그렇다.
- 모르는 것은 글 안에서 풀고, 아는 것은 풀지 않는다. 아는 것까지 풀면 글이 길어진다.

**1-3. 글 종류를 고르고 그 뼈대를 따른다**
- 종류와 뼈대는 `skeletons.md`에 있다. 종류는 원본의 형식이 아니라 주제에 맞춰 고른다.

**1-4. 원본 문서가 아니라 원본이 다루는 주제를 쓴다**
- 원본 문서를 평가하거나 풀이하지 않는다. 원본이 이야기하는 것을 사람이 읽기 편한 형태로 풀어서 설명한다. 새 글의 주어는 원본 안의 시스템, 데이터, 결정이고, 원본 문서가 주어가 되지 않는다.
- 원본의 순서와 목차를 따르지 않는다. 주제에 맞는 뼈대로 다시 짠다.
- 구성은 바꿔도 내용은 해치지 않는다. 원본의 주장, 사실, 숫자를 빼거나 바꾸지 않고, 내 의견을 섞지 않는다.
- 원본을 가리키는 말은 맨 끝 "출처"에 한 번만 쓴다. 본문에 "원문은", "보고서에 따르면", "원본의 말" 칸을 두지 않는다.
- 원본이 정하지 않은 것은 "원문에 없음"이 아니라 주제의 상태로 쓴다. ○ 아직 정하지 않았습니다.
- ✗ 원문은 배포 전에 캐시를 먼저 비워야 한다고 봅니다.
- ○ 배포 전에 캐시를 먼저 비워야 합니다.
- ✗ 용어 표에 "원문의 말" 칸을 둔다.
- ○ 용어 표에는 이 글에서 쓰는 말만 둔다.

**1-5. 보태는 지식은 짧게 넣고, 보탠 곳을 표시한다**
- 읽는 데 필요한 지식이 원본에 빠져 있을 때만 보탠다. 꼴은 세 가지다.

| 꼴 | 언제 | 표시 |
|---|---|---|
| 한두 문장 | 용어나 이름 하나를 그 자리에서 풀 때 | 표시하지 않는다 |
| 주석 | 배경, 예시, 원본과 다른 사실을 알릴 때 | `> [!note] 덧붙임` 인용 블록, 또는 "덧붙임:"으로 시작하는 문단 |
| 덧붙인 절 | 원본을 읽기 전에 알아야 할 것이 한 문단을 넘을 때 | 절 제목 끝에 "(덧붙임)" |

- 원본의 주장이 조사한 사실과 다르면 원본의 주장을 고쳐 쓰지 않고 주석으로 알린다. ○ 덧붙임: 코드로 확인하니 만료 시간은 30분이 아니라 5분입니다 (`application.yml`의 `token.ttl`).
- 보탤 것이 주석과 덧붙인 절로 감당되지 않으면 더 쓰지 않는다. 따로 배워야 할 주제가 무엇인지 사용자에게 알린다.

## 2. 낱말과 가리키기

**2-1. 처음 나오는 용어에는 그 자리에서 종류와 뜻을 붙인다**
- 종류는 규격 용어, 추상 개념, 인터페이스, 클래스, 어노테이션, 테이블, 컬럼, HTTP 헤더, URL 경로, 문자열 값, 설정 키, 명령어, 프로젝트가 지은 이름 가운데 하나다. 특정 제품에만 있는 개념은 제품 이름을 붙인다(예: Keycloak 개념). 라이브러리의 것인지 우리 코드의 것인지도 함께 적는다.
- 한 글에 이런 용어가 세 개 이상이면 글 앞에 용어 표를 둔다. 칸은 "용어 / 종류 / 뜻 / 예"다.
- ✗ CI는 이력을 얕게 받아 이 ref가 없습니다.
- ○ CI는 저장소를 받을 때 최근 커밋 몇 개만 받습니다(얕은 clone). 그래서 비교 기준인 `origin/develop` 브랜치가 CI 안에 없습니다.

**2-2. 작업 중에 스스로 붙인 이름은 쓰지 않는다**
- 프로젝트가 문서나 코드에 정해 둔 이름은 지어낸 이름이 아니다. 그 이름은 그대로 쓰고 종류를 "프로젝트가 지은 이름"으로 붙인다.
- 그 이름이 가리키는 대상을 그대로 쓴다. 이름을 붙였다는 것 자체를 읽는 사람은 모른다.
- ✗ 옛 API, 같은 아이디, 새 경로
- ○ `legacy-api` 앱의 `GET /v1/books/{bookId}`, `members.login_id` 컬럼

**2-3. 대상은 찾아갈 수 있는 이름으로 가리킨다**

| 대상 | 적는 것 |
|---|---|
| 코드 | 파일 경로, 클래스, 메서드. 필요하면 줄 번호 |
| API | 앱 이름, HTTP 메서드, 경로 |
| 데이터 | `테이블.컬럼`과 조건 |
| 문서 | 파일 경로와 장 제목 |
| 사람이 한 일 | 누가, 어디에, 무엇을 |

- ✗ 그 경로를 이번에 처음 만들었습니다.
- ○ 신입이 혼자 읽을 온보딩 문서는 지금까지 없었습니다. 이번에 제가 `docs/onboarding/`에 처음 만들었습니다.

**2-4. 번호와 지시어만으로 가리키지 않는다**
- "4번", "1-A", "위의 것", "이 ref", "해당 값"은 앞을 다시 찾아 읽게 만든다. 번호 뒤에 무엇인지 붙이거나 이름을 다시 쓴다.
- ✗ 4번은 아직 확인하지 않았습니다.
- ○ 4번(응답 헤더에 회원 번호가 들어 있는지)은 아직 확인하지 않았습니다.

**2-5. 쉽게 쓰라는 요청을 비유로 바꾸지 않는다**
- "쉽게", "그림 위주로"는 글을 그림과 표로 바꾸고 예시를 붙이라는 뜻이다. 정확한 용어는 그대로 두고, 그 용어가 무엇인지를 덧붙인다.
- ✗ 필터는 건물 입구의 경비원과 같습니다.
- ○ `SecurityFilterChain`은 요청이 컨트롤러에 닿기 전에 차례로 실행되는 필터 목록입니다. (필터가 실행되는 순서 그림을 이어서 붙임)

**2-6. 화면에 보이는 이름과 같은 이름을 쓴다**
- 상태창, 콘솔 로그, 웹 화면, CLI 출력에 뜨는 이름이 있으면 그 이름을 쓴다. 다르게 부르면 읽는 사람은 다른 것으로 읽는다.
- ✗ CI 화면에 `lint`, `test` 잡이 떠 있는데, 글에서는 "검사 단계", "시험 단계"로 부른다.
- ○ `lint` 잡, `test` 잡

## 3. 내용

**3-1. 결정이나 문제를 말하기 전에 지금 상태를 먼저 쓴다**
- 지금 무엇을 쓰고 있는지, 어떻게 동작하는지, 데이터가 어디에 어떤 모양으로 들어가는지를 앞에 적는다.
- ✗ 세션 저장소를 Redis로 옮길지 정해 주세요. 보안 문제가 있습니다.
- ○ 지금은 로그인 세션을 서버 메모리에 둡니다. 서버가 두 대라서, 요청이 다른 서버로 가면 로그인이 풀립니다. (요청이 두 서버로 갈리는 그림) 그래서 세션을 Redis로 옮길지 정해야 합니다.

**3-2. 무엇을 물을 때는 왜 정해야 하는지와 고르면 무엇이 달라지는지를 함께 쓴다**
- 고르는 쪽마다 결과를 예시 데이터로 보여 준다.
- ✗ 어느 쪽을 먼저 만들까요?
- ○ 새 API를 처음 부를 쪽을 정해야 합니다. 관리자 화면이 먼저 부르면 권한 확인을 먼저 만들어야 하고, 회원 앱이 먼저 부르면 회원 토큰 검증을 먼저 만들어야 합니다.

**3-3. 추상적인 설명 바로 뒤에는 실제 모습을 하나 붙인다**

| 설명하는 것 | 붙일 것 |
|---|---|
| 데이터가 어떻게 바뀌는지 | 테이블 행 2~3개, 바뀌기 전과 후 |
| 코드가 어떻게 동작하는지 | 10줄 안팎의 코드와 들어가는 값, 나오는 값 |
| git, CI | `A ─ B ─ C` 꼴의 커밋 그림 |
| 문서·설정 변경 | 원문과 수정본, 또는 diff |
| API | curl 한 줄과 응답 JSON |
| 결정 | 고르는 쪽마다 "이 회원은 로그인된다 / 안 된다" 같은 결과 |

- ✗ 같은 내용이면 지문이 같아서 충돌합니다.
- ○ 두 파일의 내용이 `hello`로 같으면 지문은 둘 다 `2cf24d…`가 됩니다. (두 행을 나란히 보여 주는 표)

**3-4. 다른 문서나 다른 에이전트가 쓴 문장을 그대로 옮기지 않는다**
- 에이전트가 읽으라고 쓴 문서와 보고는 명사를 줄줄이 붙인 꼴이 많다. 사람이 읽게 동사로 풀어 다시 쓴다.
- ✗ 일반 회원 토큰은 403입니다.
- ○ 일반 회원 계정으로 받은 토큰으로 관리자 API를 부르면 403을 돌려줍니다.
- ✗ 아직 제거되지 않은 레거시 화면이 상한 없는 결과를 그대로 받아야 하는 조회
- ○ `admin-web`의 회원 목록 화면은 아직 남아 있습니다. 이 화면은 회원 목록을 한 번에 모두 받습니다. 그래서 이 화면이 부르는 조회에는 개수 제한을 걸 수 없습니다.

**3-5. 확인한 것과 추측한 것을 나눠 적는다**
- 무엇으로 확인했는지 적는다. 코드를 읽었는지, 실행했는지, 문서에서 봤는지가 다르다.
- ○ 코드로 확인했고 실행하지는 않았습니다. / 확인 못 함.

**3-6. 묻지 않은 것은 넣지 않는다**
- 작업 과정, 검토 이력, 덧붙인 교훈은 사용자가 물었을 때만 쓴다.
- 사람이 읽는 PR 본문은 1,000자 안쪽으로 쓰고, 자세한 것은 접기에 둔다.
- 이미 답이 있는 것을 질문으로 만들지 않는다. 묻는 것은 서로 어긋나는 것, 비어 있는 것, 사람이 판단해야 하는 것뿐이다.

## 4. 그림

**4-1. 그림 종류는 질문에 맞춰 고른다**

| 질문 | 그림 |
|---|---|
| 누가 누구에게 무엇을 보내는가 | `sequenceDiagram` (`autonumber`) |
| 어떤 조건에서 어디로 갈리는가 | `flowchart` |
| 무엇이 어떻게 저장되는가 | `erDiagram`, 또는 실제 테이블 행 |
| git 이력이 어떻게 생겼는가 | 커밋 그림 (`A ─ B ─ C`) |
| 무엇이 바뀌었는가 | 바뀌기 전과 후를 나란히 놓은 그림 두 장 |

**4-2. 큰 그림 한 장을 먼저 두고, 그림 하나에는 질문 하나만 담는다**
- 큰 그림에는 참여자 전체와 주요 요청·응답이 한 장에 들어간다. 자세한 그림은 그다음에 따로 그린다.
- 그림 하나가 두 가지를 말하면 둘로 나눈다.

**4-3. 참여자는 실제 이름으로 쓴다**
- 앱 이름, 서버 이름, 브라우저, 테이블 이름을 쓴다. "서버 A", "외부 시스템"처럼 쓰지 않는다.

**4-4. 화살표마다 주고받는 값을 적는다**
- 요청은 `HTTP 메서드 경로 · 핵심 값`, 응답은 `상태 코드 · 돌려주는 값`으로 적는다.
- `sequenceDiagram`에서 응답은 점선(`-->>`)으로 그린다. `flowchart`에서는 `-->|글씨|` 꼴로 적는다.
- `flowchart`에서 요청과 응답을 화살표 하나(`<-->`)로 그릴 때는 `▶ 보내는 것<br/>◀ 받는 것` 꼴로 적는다.
- ✗ `W->>A: 요청`
- ○ `W->>A: POST /oauth2/token · grant_type, username, password`

**4-5. 있어야 할 것 같은데 그림에 없는 것은 이유와 함께 적는다**
- 그림 바로 아래에 한 줄로 둔다. 적지 않으면 읽는 사람은 빠뜨렸다고 읽는다.
- ○ 그림에 없는 것: 결제 서버로 가는 화살표. 이 흐름에서는 결제 API를 부르지 않음.

**4-6. 색이나 모양으로 나눈 것은 범례로 밝힌다**
- 우리 코드와 라이브러리, 이미 있는 것과 새로 만드는 것, 확인한 것과 추측한 것을 나눌 때 쓴다.
- 색을 쓰면 아래 `classDef` 값을 쓴다.
  - 우리 코드: `common fill:#dbeafe,stroke:#2563eb,color:#1e3a8a`
  - 도메인·업무 규칙: `domain fill:#fef3c7,stroke:#d97706,color:#78350f`
  - 거절·실패: `bad fill:#fee2e2,stroke:#dc2626,color:#7f1d1d`
  - 성공·실행: `good fill:#dcfce7,stroke:#16a34a,color:#14532d`
  - 외부(남의 서버·규격): 기본색

**4-7. 화살표가 겹치거나 노드가 아홉 개를 넘으면 그림을 나눈다**
- 노드 글씨는 세 줄 이내로 쓴다. 긴 설명은 그림 아래 표로 뺀다.
- 그림 아래 표의 칸은 "# / 부르는 쪽 → 받는 쪽 / API / 보내는 값 / 받는 값 / DB 읽기·쓰기 / 코드 위치"다. 쓰지 않는 칸은 뺀다.

**4-8. 움직이는 그림은 버튼으로 한 단계씩 넘기게 만든다**
- 저절로 넘어가면 읽기 전에 지나간다.
- 단계마다 "들어가는 값 / 하는 일 / 부르는 것 / 돌려주는 값" 네 칸을 둔다.

**4-9. 넣기 전에 렌더해서 확인한다**
- `scripts/check.py`가 mermaid를 렌더한다. 깨진 그림은 내보내지 않는다. 렌더하지 못했으면 그림을 확인하지 못했다고 알린다.
