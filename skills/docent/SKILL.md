# docent

읽기 어려운 문서, 대화 내용, 작업 결과물을 읽는 사람이 이해할 수 있게 풀어 쓰는 절차다. 무엇을 지키는지는 `references/rules.md`가, 글 종류별 순서는 `references/skeletons.md`가, 검사는 `scripts/check.py`가 갖는다. 이 파일은 왜 있는지와 순서만 정한다.

## 왜 있나

누가 쓴 제안서, 에이전트의 작업 보고, 길게 이어진 대화처럼 **내용은 있는데 읽기가 어려운 것**이 있다. 쓴 쪽은 작업하면서 익숙해진 낱말과 이름을 풀지 않고 쓰고, 지금 상태와 예시를 건너뛴다. 읽는 사람은 그것을 모른다. 그래서 "이게 뭔데?" 하고 되묻게 된다.

docent는 그 글이 이야기하는 것을 읽는 사람 옆에서 안내하듯 풀어서 설명한다. 이름은 미술관에서 관람객에게 작품을 설명하는 사람을 뜻하는 docent에서 왔다. 목표는 하나다. **이 글만 읽고, 되묻지 않고 원본이 하려던 말을 이해한다.**

지키는 것은 네 가지다.

| 지키는 것 | 뜻 |
|---|---|
| 주제를 설명한다 | 원본 문서를 평가하거나 풀이하지 않는다. "원문은 ~라고 봅니다"처럼 문서에 대해 말하지 않고, 원본이 다루는 시스템, 데이터, 결정을 주어로 쓴다 |
| 구성은 다시 짠다 | 원본의 순서와 목차를 따르지 않는다. 읽는 사람이 이해하기 쉬운 순서로, 주제에 맞는 뼈대로 다시 짠다 |
| 내용은 해치지 않는다 | 원본의 주장, 사실, 숫자를 빼거나 바꾸지 않는다. 내 의견을 섞지 않는다 |
| 필요한 지식만 짧게 보탠다 | 읽는 데 필요한 지식이 빠져 있으면 한두 문장, 주석, 덧붙인 절로 보탠다. 주석과 덧붙인 절은 표시해서 원본의 내용과 구별되게 한다 |

재료는 가리지 않는다. 문서, PDF, 회의록, 대화 내용, 코드와 조사 결과가 모두 재료다. 읽는 사람은 원본을 열어 보지 않아도 되고, 원본이 있다는 것을 몰라도 된다.

## 다른 스킬과 나누는 일

세 스킬은 같은 플러그인(korean-developer-skills)에 들어 있고, 하는 일이 서로 다르다. docent와 make-textbook은 서로의 파일을 읽지 않는다.

| 스킬 | 언제 | 결과물 |
|---|---|---|
| korean-sentences | 내용은 이해되는데 문장이 어색할 때 | 같은 글. 낱말, 개발 용어, 말투만 고친다. 사실은 더하지 않는다 |
| docent | 문서나 결과물의 내용이 이해되지 않을 때 | 원본이 이야기하는 것을 읽기 편한 구성으로 풀어 쓰고, 필요한 지식을 짧게 보탠 새 글 |
| make-textbook | 기반 지식을 모르는 것이라 처음부터 배워야 할 때 | 한 권을 정독하면 되는 교과서 |

- docent는 글을 쓰면서 korean-sentences의 문장 규칙을 함께 따른다.
- 보탤 지식이 주석과 덧붙인 절로 감당되지 않을 만큼 많으면, docent로 끝내지 않고 make-textbook을 권한다. 원본을 읽기 전에 배워야 할 것이 있다는 뜻이기 때문이다.

## 언제 쓰나

- 받은 문서, 제안서, 보고서, PDF, 회의록이 읽기 어려울 때
- 대화 내용이나 작업 결과를 사람이 읽을 글로 정리할 때: 작업 보고, PR·이슈 본문, 현황 조사, 설계, API 흐름, 결정 요청
- 대화의 짧은 답(몇 줄)에는 절차를 다 밟지 않는다. `references/rules.md`의 2장과 3장만 지킨다.

## 절차

| 단계 | 하는 일 |
|---|---|
| 1. 읽고 정한다 | 원본을 끝까지 읽고, 읽는 사람과 막히는 곳을 정한다 |
| 2. 조사한다 | 막히는 곳을 메울 실제 이름, 예시, 빠진 지식을 찾는다 |
| 3. 뼈대대로 쓴다 | 고른 글 종류의 뼈대대로 쓰고, 필요한 지식을 보탠다 |
| 4. 그림을 그린다 | 큰 그림 한 장과 자세한 그림 |
| 5. 검사한다 | 그림 렌더, 글자 검사, 원본에서 빠진 것 |
| 6. 다시 읽는다 | 처음 읽는 사람으로 읽고, 긴 글은 서브에이전트에게 읽힌다 |
| 7. 내보낸다 | 경로, 보탠 것, 확인 못 한 것을 알린다 |

### 1. 읽고 정한다

`references/rules.md`를 처음부터 끝까지 읽는다. 원본을 끝까지 읽는다. 그다음 아래 네 가지를 정한다. 글에 적지는 않아도 된다.

- **이 글이 답할 질문 한 문장.** 원본이 이야기하려는 것에서 잡는다. 질문이 둘이면 글을 둘로 나누거나, 절을 나눈다.
- **읽는 사람이 아는 것과 모르는 것.** 메모리나 프로젝트 규칙(`CLAUDE.md`, `AGENTS.md`)에 사용자가 아는 것이 적혀 있으면 그것을 따른다. 적혀 있지 않으면 "이 글을 처음 여는 개발자"를 읽는 사람으로 둔다.
- **막히는 곳.** 원본을 읽는 사람의 눈으로 읽으며 되묻게 될 곳을 표시한다. 풀지 않은 용어, 지어낸 이름, 무엇인지 모를 번호와 지시어, 지금 상태 없이 나온 결정, 예시 없는 설명, 값이 없는 그림이 그런 곳이다.
- **글 종류.** `references/skeletons.md`의 표에서 고른다. 종류는 원본의 형식이 아니라 주제에 맞춰 고른다. 원본이 20쪽 보고서여도 주제가 API 흐름이면 API 흐름 뼈대를 쓴다.
- **원본의 내용 목록.** 원본의 주장, 사실, 숫자를 적어 둔다. 구성을 다시 짜면서 빠뜨리지 않으려는 것이고, 5단계에서 이 목록과 대조한다.

### 2. 조사한다

1단계에서 표시한 막히는 곳을 메우려고 조사한다. 원본의 낱말이 가리키는 것을 추측으로 채우지 않는다.

- 코드: 경로, 클래스, 메서드. 프로젝트 규칙에 코드를 찾는 방법이 정해져 있으면 그 방법을 따른다.
- API: 앱 이름, HTTP 메서드, 경로, 요청·응답의 실제 필드
- 데이터: `테이블.컬럼`과 실제 값의 예 2~3개
- 문서: 파일 경로와 장 제목
- 화면: 상태창, 콘솔, 웹 화면에 실제로 뜨는 이름
- 빠진 지식: 원본이 안다고 치고 넘어간 개념. 한두 문장으로 풀 수 있는 만큼만 찾는다.

확인하지 못한 것은 지어내지 않고 글에 "확인 못 함"이라고 적는다. 원본의 주장이 사실과 다른 것을 찾았으면 본문을 고치지 않고 주석으로 알린다 (규칙 1-5).

### 3. 뼈대대로 쓴다

`references/skeletons.md`에서 고른 종류의 뼈대대로 쓴다. 쓰는 동안 아래 두 가지를 함께 따른다.

- `references/rules.md`의 규칙
- 문장 규칙: 이 스킬 폴더 옆의 `../korean-sentences/references/rules.md`와 같은 폴더의 `terms/` 목록

보태는 지식은 세 가지 꼴로만 넣는다 (규칙 1-5).

| 꼴 | 언제 | 표시 |
|---|---|---|
| 한두 문장 | 용어 하나나 이름 하나를 그 자리에서 풀 때 | 따로 표시하지 않는다. 원본의 주장을 바꾸지 않는 풀이이기 때문이다 |
| 주석 | 배경, 예시, 원본과 다른 사실을 알릴 때 | `> [!note] 덧붙임` 인용 블록, 또는 "덧붙임:"으로 시작하는 문단 |
| 덧붙인 절 | 원본을 읽기 전에 알아야 할 것이 한 문단을 넘을 때 | 절 제목 끝에 "(덧붙임)" |

원본이 파일이면 덮어쓰지 않고 새 파일로 쓴다. 사용자가 원본을 고치라고 했을 때만 원본을 고친다.

### 4. 그림을 그린다

`references/rules.md` 4장을 따른다. 큰 그림 한 장을 먼저 그리고, 자세한 그림은 따로 그린다. 그림마다 위에 "이 그림이 답하는 질문"을 한 줄로 둔다. 그림에는 원본의 내용과 조사해서 확인한 것만 담는다.

### 5. 검사한다

파일로 남기는 글은 두 검사를 돌린다. 대화로만 쓰는 글은 mermaid를 넣었을 때만 임시 파일로 저장해 돌린다.

```
python3 <이 스킬 폴더>/scripts/check.py <다시 쓴 글.md>
python3 <이 스킬 폴더>/../korean-sentences/scripts/check.py <다시 쓴 글.md> --before <원본.md>
```

- "실패"는 렌더가 깨진 그림이다. 고칠 때까지 내보내지 않는다.
- "경고"는 하나씩 본다. 고칠 것은 고치고, 일부러 남긴 것은 보고에 이유를 적는다.
- `--before`는 원본이 Markdown이나 HTML 파일일 때 붙인다. 원본에 있던 코드, 링크, 숫자가 다시 쓴 글에서 사라졌으면 경고한다. 사라진 것은 되살린다. 구성을 다시 짰으므로 사라진 것만 보고, 순서가 달라진 것은 문제 삼지 않는다. 원본이 PDF나 대화 내용이면 `--before` 없이 돌리고, 1단계에서 적어 둔 내용 목록과 직접 대조한다.
- 그림을 렌더할 브라우저를 찾지 못하면 검사가 "렌더 못 함"이라고 경고한다. 그때는 그림을 확인하지 못했다고 보고에 적는다.
- 검사는 글자만 본다. 통과했다고 규칙을 다 지킨 것은 아니다.

### 6. 처음 읽는 사람으로 다시 읽는다

쓴 글을 처음부터 읽으며 `references/rules.md` 맨 끝의 "내보내기 전 점검"을 하나씩 확인한다. 걸리는 것이 있으면 고친다.

긴 글은 서브에이전트에게 읽혀 본다. 글을 쓴 세션보다 가벼운 모델(예: `model: "sonnet"`)로 띄우고, 이 대화 내용과 원본은 주지 않는다. 다시 쓴 글의 경로만 주고 "처음 보는 낱말, 무엇을 가리키는지 모르는 말, 예시 없이 넘어간 설명, 화살표에 값이 없는 그림을 줄 번호와 함께 찾아 달라"고 한다. 돌아온 것을 고친다.

### 7. 내보낸다

- 파일로 남겼으면 경로를 알린다.
- 보탠 것(주석과 덧붙인 절)을 한두 줄로 알린다.
- 일부러 남긴 경고, 확인 못 한 것, 원본과 사실이 다르다고 주석을 단 곳을 알린다.

## 규칙을 고칠 때

사용자가 docent로 쓴 글을 가리키며 이해가 안 된다고 하면, 그 문장만 고치고 끝내지 않는다. 같은 글이 다음에도 나오지 않게 원인을 고친다.

1. 왜 막혔는지 따진다. 이미 있는 규칙을 어긴 것인지, 규칙에 없는 것인지 나눈다.
2. 규칙을 어긴 것이면 절차의 어느 단계에서 놓쳤는지 찾아 그 단계를 고친다.
3. 규칙에 없는 것이면 바꿀 내용을 사용자에게 먼저 보여 주고 확인받는다.
4. 확인받은 규칙을 `references/rules.md`의 알맞은 장 끝에 다음 번호로 더한다. 번호는 바꾸지 않는다. 사례는 `references/cases.md`에 원문, 사용자의 말, 고친 문장으로 남긴다. 회사나 프로젝트에만 있는 낱말은 규칙의 ✗·○ 예시와 사례에 쓰지 않고 일반적인 예로 바꾼다.
5. 글자만 보고 찾을 수 있는 것이면 `scripts/check.py`나 `scripts/figures.py`에도 검사를 더한다.
