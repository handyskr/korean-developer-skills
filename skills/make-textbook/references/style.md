# 출력 규격

교과서의 모든 노트가 따르는 규격이다. 검토 에이전트와 `scripts/check.py`가 이 파일을 기준으로 본다. 이 스킬은 다른 스킬의 파일을 읽지 않으므로, 교과서를 쓰는 데 필요한 규격은 모두 이 파일에 있다.

## 1. 그릇

- 교과서 하나 = 폴더 하나. `목차 노트` + `N장 <제목>.md` + (있으면) `현황 <주제> (코드 기준).md`, `설계 <주제>.md`.
- 노트는 옵시디언 마크다운. 머리말(frontmatter)에 `title`, `tags`, `작성일`, 설계 노트는 `상태: 제안 | 결정`.
- 그림은 mermaid. 큰 그림이 mermaid로 깨질 때만 HTML 안 손 SVG를 허용하고, 노트에서 링크한다.
- 시뮬레이터(한 단계씩 넘기는 HTML)는 요청한 장에만. 버튼으로 한 단계씩 넘기게 만들고, 단계마다 "들어가는 값 / 하는 일 / 부르는 것 / 돌려주는 값" 네 칸을 둔다.
- 책은 그 책만 정독하면 되게 쓴다. 다른 문서를 읽어야 이해되는 곳을 남기지 않는다. 더 깊이 갈 사람을 위한 링크는 `## 근거`에만 둔다.

## 2. 장의 고정 뼈대 (순서 고정)

1. `[!abstract] 한 줄 결론`
2. `[!info]- 이 장의 용어 표` (접힘). 칸은 "용어 / 종류 / 뜻 / 예"다.
3. **큰 그림 한 장.** 주체·요청·응답이 한 그림에. 읽는 순서를 그림 위에 ①②③ 으로.
4. 절들. 각 절은 **그림 → 표 → 짧은 설명** 순서. 글이 그림을 설명하지, 그림이 글을 장식하지 않는다.
5. (프로젝트 기반 책이면) `현황` 링크. 지금 코드에서는 어떻게 되어 있나, 파일:줄.
6. `[!summary] 되짚기` 다섯 줄 이내.
7. `지금 정할 것` 결정 표: 결정 / 추천 / 이유.
8. `근거`. 사실 검토에서 확인한 공식 문서·규격의 URL.

장 맨 위에 "이 장의 목적: ~을 하기 위해 필요한 만큼만" 한 줄. 목적에 안 닿는 내용은 `[!note]- 더 보기` 접힘으로.

## 3. 그림

| 무엇 | 다이어그램 |
|---|---|
| 흐름(누가 누구에게 무엇을) | `sequenceDiagram`, `autonumber` |
| 조건에 따라 갈리는 길 | `flowchart` |
| 구조(테이블·객체) | `erDiagram`, `classDiagram` |
| 시간에 따른 변화 | `timeline` |

- 그림 하나는 주장 하나. 두 가지를 말하면 둘로 나눈다. 노드가 아홉 개를 넘어도 나눈다.
- 화살표에는 반드시 글씨를 적는다.
  - `sequenceDiagram`: 요청은 실선(`->>`), 응답은 점선(`-->>`)으로 따로 긋는다. 요청은 `HTTP 메서드 경로 · 핵심 값`, 응답은 `상태 코드 · 돌려주는 값`으로 적는다.
  - `flowchart`: `-->|글씨|` 꼴로 적는다. 큰 그림에서 요청과 응답을 화살표 하나(`<-->`)로 그릴 때는 `▶ 보내는 것<br/>◀ 받는 것` 꼴로 적는다.
  - 목차 노트의 장 사이 화살표에는 "먼저 읽기"처럼 관계를 적는다.
- 참여자는 실제 이름으로 쓴다. "서버 A", "외부 시스템"처럼 쓰지 않는다.
- 노드 글씨는 세 줄 이내. 긴 설명은 그림 아래 표로.
- 책임 경계는 색으로 고정한다. `classDef` 이름과 값을 책 전체에서 같게.
  - 공통 모듈·우리 코드: `common fill:#dbeafe,stroke:#2563eb,color:#1e3a8a`
  - 도메인·업무 규칙: `domain fill:#fef3c7,stroke:#d97706,color:#78350f`
  - 거절·실패: `bad fill:#fee2e2,stroke:#dc2626,color:#7f1d1d`
  - 성공·실행: `good fill:#dcfce7,stroke:#16a34a,color:#14532d`
  - 외부(남의 서버·규격): 기본색
- subgraph는 "같은 책임" 묶음에만. subgraph끼리 화살표를 그으면 "모두 같은 모양으로"라는 뜻이 된다.
- `classDiagram`에서 괄호가 든 멤버는 메서드로 그려지니 피한다. 긴 줄은 겹치니 나눈다.
- 라벨 안에 `<`, `>`를 쓰지 않는다(HTML로 먹힌다). 따옴표로 감싼다.
- 넣기 전에 반드시 렌더 확인(`scripts/check.py`). 렌더하지 못했으면 그림을 확인하지 못했다고 알린다.

## 4. 용어

- **비유 금지.** "마치", "비유하자면", "~라고 생각하면", 역할극(문지기·장부·도장 등)을 쓰지 않는다. 어려우면 그림을 하나 더 그린다.
- 용어가 본문에 처음 나올 때 바로 뒤에 `*(종류)*` 꼴로 **종류**를 붙인다. 예: `SecurityFilterChain` *(인터페이스)*. 종류 목록:
  `*(규격 용어)*` `*(추상 개념)*` `*(인터페이스)*` `*(클래스)*` `*(어노테이션)*` `*(테이블)*` `*(컬럼)*` `*(HTTP 헤더)*` `*(URL 경로)*` `*(문자열 값)*` `*(설정 키)*` `*(명령어)*` `*(프로젝트가 지은 이름)*`
  특정 제품에만 있는 개념은 제품 이름을 붙인다. 예: `*(Keycloak 개념)*`, `*(Spring 빈)*`
- 한 문장에 종류 태그가 둘 넘게 붙으면 문장에서 빼고 장의 용어 표에만 적는다.
- 작성 에이전트가 쓰다가 스스로 붙인 이름은 쓰지 않는다. 그 이름이 가리키는 대상을 그대로 쓴다. `*(프로젝트가 지은 이름)*`은 프로젝트의 문서나 코드에 이미 있는 이름에만 붙인다.
- 약어는 원말과 함께 쓴다. 책 전체의 약어 표는 목차 노트에 하나 두고, 칸은 "약자 / 원말 / 역할 / 누가 정함 / 예"다. 장의 용어 표와는 다른 표다.
- 영어 식별자는 백틱으로 그대로. 설명은 우리말.
- 같은 것을 두 이름으로 부르지 않는다. 책 전체에서 한 이름.

## 5. 문장

- 결론 먼저, 이유 뒤.
- 한 문장에 한 가지. 20어절 안팎.
- 쉬운 우리말. 주어와 서술어를 갖춘다. 번역투("~에 대해", "~에 있어서", "~되어진다", "~함으로써")와 어려운 한자어("기술하다", "명시하다", "도출", "수행", "제반")를 피한다.
- 개발 용어는 한국 개발자가 실제로 쓰는 말로 쓴다. ○ 통합 테스트, `orders` 테이블 ✗ 통합 시험, `orders` 표
- "~할 수 있다"로 뭉개지 않는다. "~한다 / ~하지 않는다"로 쓴다.
- 추상적인 설명 바로 뒤에는 실제 모습을 하나 붙인다. 테이블 행 2~3개, 10줄 안팎의 코드와 들어가는 값·나오는 값, curl 한 줄과 응답 JSON 같은 것이다.
- 숫자·경로·코드는 표나 코드 블록으로. 문장 안에 넣지 않는다.
- 작성 때 확신이 없는 주장은 `(확인 필요)`, 검토 뒤에도 근거를 찾지 못한 주장은 `(미확인)`으로 적는다. 프로젝트 기반 책에서 실행해 보지 않은 것은 "코드로 확인했고 실행하지는 않았다"고 적는다.

## 6. 현황 노트와 설계 노트

프로젝트 기반 책에만 둔다.

- 현황 노트: 코드 기준. 절마다 ① 설정 파일과 체인 ② API 표(경로·요청·응답·파일:줄) ③ 요청 때 확인하는 흐름 ④ 데이터 모델. 맨 끝에 위험 표와 "어디부터 볼지" 파일 지도. 기준 커밋과 조사일을 머리말에.
- 설계 노트: 머리말에 `상태`. 맨 앞에 큰 그림. 맨 끝에 `지금 정할 것` 표. 현황 노트를 링크해 "무엇을 고치려는 제안인지" 한 줄.
